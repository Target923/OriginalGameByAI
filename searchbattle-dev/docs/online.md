# サーチバトル オンライン対戦（めっちゃカメレオン型・P2P）

2026-10-25 に設計し、同じ日に v1 を作った。しくみを学ぶための説明と、次に手を入れるときの地図を兼ねる。

## 1. ねらいと範囲

- **v1（できたもの）**：1vs1 の単発試合をオンラインで遊べる。ルール（予選4×4・決勝5×5）とアイテムの設定（選ぶ・ランダム・ドラフト）は、部屋を作った人が決める。決着のあと、部屋を作った人が「もう一度」で同じ相手と次の試合を始められる。大会モードは対象外。
- **方式**：部屋を作った人（**ホスト**）の端末が審判をする。相手（**ゲスト**）は操作を送り、判定の結果を受け取って画面を描く。
- **サーバー代は0円**：つなぎ役に PeerJS の無料クラウドを使い、試合のデータは端末どうしで直接やりとりする（ブラウザに入っている WebRTC）。めっちゃカメレオンが EOS（無料のマッチング・中継）を使い、部屋を立てた人の PC がサーバー役になっているのと同じ考え方。
- **割り切り**：ホストは、開発者ツールを使えば相手の配置をのぞける。知り合いどうしで遊ぶ前提。ゲストには見てよい情報しか送らないので、ゲストはのぞけない。ゲストが改造したゲームで操作を送っても、ホストのルールのプログラムが確かめるので、ルールにない手は通らない。

## 2. 用語（勉強用）

| 用語 | 意味 |
| --- | --- |
| P2P（ピア・ツー・ピア） | サーバーを通さず、端末どうしが直接つながること |
| WebRTC | ブラウザに最初から入っている、端末どうしを直接つなぐ機能。ビデオ通話にも使われる。ここでは文字のデータを送る「データチャネル」だけを使う |
| シグナリング | 直接つながる前に、お互いの「住所」（つなぎ方の情報）を交換すること。これだけは仲介役が要る。PeerJS の無料クラウドがその役 |
| STUN・TURN | STUN＝自分の外から見た住所を教えてもらうしくみ。TURN＝直接つながらないときにデータを中継するしくみ。PeerJS は、何も指定しなければ Google の STUN と PeerJS の TURN を使う（このゲームもそのまま使う） |
| ホスト権威（host-authoritative） | 本当の盤面を持って判定するのはホストだけ、という作り方。ゲストの端末は「見てよい情報」で画面を描くだけ |
| スナップショット | ある時点のゲームの状態をまるごと写したデータ。ホストが判定のたびにゲスト向けのものを作って送る |
| 伏せる（redaction） | ゲストに送るスナップショットから、ゲストが知ってはいけない部分（ホストのキューブの位置など）を取り除くこと |
| 合図（ping） | 「まだつながっているよ」と4秒ごとに送り合う小さなメッセージ。相手がタブを閉じたとき、「切れた」の知らせが来ないことがあるので、45秒何も届かなければ切れたとみなす |

## 3. 全体の流れ

```
 ホスト（審判）              PeerJS の無料クラウド          ゲスト
 ─────────────              ───────────────────          ─────────────
 部屋を作る ───登録 "searchbattle-K7P2QX"──▶
 部屋コード K7P2QX を表示
                                            ◀──"searchbattle-K7P2QX" を探す── コードを入力
           ◀════════ WebRTC で直接つながる（ここから先、クラウドは使わない）════════▶
           ◀──────────────── hello（アプリ名・通信とゲームの版・名前）───────────────
 試合を作る（ホストの設定で）
 ──────────── welcome（伏せたスナップショット。ゲストはこの中で配置する）────────────▶
 配置する                                                  配置する（自分の画面の中だけ）
           ◀──────────── setup（形・向き・位置・トレジャーのマス）──────────────
 ルールで1つずつ置き直して確かめる
 ────────────────── state（ゲスト向けに伏せたスナップショット）──────────────▶
 対戦：ゲストの手番
           ◀──────────────── act（例：call、マス 5、通し番号 seq）──────────────
 g.call(1, 5) で判定
 ────────────────── state（結果。新しい演出の記録も入る。ack＝処理した番号）──▶  演出を見せて描く
 対戦：ホストの手番
 g.useItem(0, ...) で判定
 ────────────────── state ─────────────────────────────────────────────▶  演出を見せて描く
 決着
 ────────────────── full（伏せない全部。答え合わせとリプレイ用）──────────────▶
 「もう一度」→ 新しい試合を作って welcome（ゲストは配置の画面へ）
```

## 4. メッセージ（通信の約束ごと）

どれも `{ t: '種類', ... }` の形の小さなデータ。PeerJS の既定の送り方（binary）は大きなデータを自動で分けて送るので、スナップショット（1通10KBほど）もそのまま送れる。届く順番を保つため、つなぐときに `reliable: true` を付ける（state が前後すると、古い盤面に戻ってしまう）。

| t | 向き | 中身 | いつ |
| --- | --- | --- | --- |
| `hello` | ゲスト→ホスト | `app: 'searchbattle'`、`net`（通信の版 `NET_VERSION`）、`v`（エンジンの版 `VERSION`）、`name` | つながった直後。版が違えば `bye`（version）で断る |
| `welcome` | ホスト→ゲスト | `seat`（ゲストの席＝1）、`snap`（伏せたスナップショット。配置の前の状態）、`ack` | hello を受けたとき・「もう一度」のとき |
| `setup` | ゲスト→ホスト | `pieces: [{ key, t, r0, c0 }]`（置いた順）、`treasure`（マス） | ゲストが配置完了を押したとき |
| `act` | ゲスト→ホスト | `name`（`draftPick`・`call`・`useItem`・`answer`・`skipCall`・`endTurn`・`treasureCall`・`sacrifice`）、`args`（席の番号は入れない）、`seq`（通し番号） | ゲストが操作したとき |
| `state` | ホスト→ゲスト | `snap`（伏せたスナップショット）、`ack`（最後に処理したゲストの操作の番号） | ホストが何か判定するたび（配置完了・ゲストの操作・ホストの対戦の操作） |
| `reject` | ホスト→ゲスト | `what`（`setup`／`act`）、`seq`、`reason` | ゲストの配置・操作がルール上できなかったとき（ふつうは画面側で防ぐので、まれ） |
| `full` | ホスト→ゲスト | 伏せないスナップショット（リプレイの記録 `actions` も入る）、`ack` | 決着したとき |
| `bye` | どちらも | `reason`（`version`＝版が違う／`full`＝部屋が満員／なし＝抜けた） | やめるとき・ページを閉じるとき |
| `ping` | どちらも | なし | 4秒ごと。通信路（wrapConn）の中だけで使い、Host・Guest には渡さない |

## 5. ゲストに送らないもの（伏せる）

ルールのプログラム（src/engine.js）は、もともと「本人だけに見せる情報」を分けて持っている（`priv`・`ownerPriv`）ので、それを使う。伏せるのは `redactFor(game, seat)`（src/net.js）。

| 場所 | 伏せ方 |
| --- | --- |
| ホストの `players[0].pieces` | 生きているキューブ（破片も）は消す。撃破されたキューブは公開済みなので残すが、送る項目は `DEAD_FIELDS` だけ（破片の元の個体 `fromId`、ステルスだったか、置いた時刻などは送らない） |
| 個体の番号 | 置いた順に付いているので、そのままだと「何個置いたか」の手がかりになる。撃破された順に 1, 2, 3… と付け直す（ゲストから見た相手の盤 `players[1].view.dead` の番号も同じに付け直す） |
| ホストの `treasure`・`splitPieces`・`nextId` | 消す（トレジャーのマス・バズーカで分解された元の形・次の個体の番号） |
| `first`・`cur` | 配置が終わるまで伏せる（ふつうの試合でも、配置のあとの「試合開始」で分かる） |
| `actions`（リプレイの記録） | 消す（配置の座標が入っているため）。決着後の `full` で渡す |
| `rng`・`initOpts`・CPUの方針 | 送らない（乱数はホストだけが使う） |
| `events`（演出の記録） | 数と順番はそのまま（ゲストの画面が「どこまで見せたか」を番号で覚えているため）。ホストの操作の `priv`（ワープの移動先・ステルスをかけたマス）、ホストの盤で起きたことの `ownerPriv`（バズーカで分解された個体の残りのマス）、ホストのキューブがステルスで撃破を防いだ `shield` の `cells` は消す |
| `log` | ホストの行の `priv`（本人向けの詳しい文）は消す |
| `lastAction` | ホストのステルスの `result.cells` は消す |

**送ってよい項目の一覧**で確かめる：test/net_sim.js は、ゲストに送ったどのスナップショットでも、ホストにかかわる記録（演出・ログ・直前の操作・ホストの席・撃破された個体）の項目が一覧にあるものだけかを確かめる。engine に新しい項目が増えると、このテストが失敗して気づける（そのときは、送ってよいかを考えて一覧か redactFor を直す）。

## 6. プログラムの作り

### src/net.js（新しく作った。ブラウザでは `window.SBNet`、Node では `require`）

| 部分 | 関数 | 役目 |
| --- | --- | --- |
| ① コード・名前 | `makeCode`・`normCode`・`cleanName` | 部屋のコード（6文字。0・O・1・I は使わない。全角・小文字・ハイフンは入力で直す）。名前は12文字まで、HTML の記号と「：」を取り除く（相手の画面にそのまま出るため） |
| ② 伏せる | `redactFor`・`fullSnap`・`restore` | ゲスト向けのスナップショット・決着後の全部・スナップショットから対戦を作り直す（Game の型を付け直すだけ。公開ページの更新で対戦を引き継ぐのと同じ方法） |
| ③ 中身を確かめる | `cleanArgs`・`cleanSetup` | 届いた操作・配置の形をそろえる（数の代わりに文字など、変な形のデータは断る）。最後はルールのプログラムが確かめる |
| ④ ホストの役 | `Host`（`receive`・`newMatch`・`run`・`sync`） | ゲストの hello・setup・act を受けて、ゲストの席（1番）としてだけ実行する。ホスト自身の操作は `run` で実行してから `sync` で state を送る |
| ④ ゲストの役 | `Guest`（`hello`・`receive`・`act`・`sendSetup`） | 届いた welcome・state・full で手元の対戦を差し替える。配置をまだ受け付けてもらっていないあいだは、置いている途中の配置を消さないよう差し替えない。送った操作の結果を待つあいだ（`wait`）は次を送らない |
| ⑤ PeerJS | `supported`・`loadPeerJS`・`openRoom`・`joinRoom`・`wrapConn`・`peerOptions` | `supported` はこのページで使えるか（claude.ai の公開ページは `window.claude` があるので見分けて、使えないことにする）。PeerJS 1.5.5 はオンライン対戦を始めるときだけ CDN から読み込む。部屋を作る（コードがかぶれば作り直す。2人目には `bye`（full））・入る（20秒でつながらなければあきらめる）。`wrapConn` が PeerJS のつながりを `send`・`onmessage`・`onclose`・`close` だけの「通信路」にまとめ、合図（ping）で見張る |

Host・Guest は通信のしかたを知らない（`send` 関数を渡されるだけ）。だから Node のテストでは、メッセージを直接渡して動かせる。

### src/ui.js

- **操作の窓口 `act(name, ...args)`**：人の操作で盤面を変えるところ（14か所）を、すべてこれ経由にした。ふつうの試合・大会はその場で実行（今までと同じ）、ホストは `Host.run`（実行して state を送る）、ゲストは対戦の操作を送って `{ ok: true, sent: true }` を返す（配置はゲストの手元で実行）。ゲストは送る前に、自分の盤だけで分かること（アイテムを使えるか・ワープの置き場所・アンサーの形）を `guestPrecheck` で確かめる（通信を待たずに知らせるため）。CPU の手（cpuRun など）は今までどおり直接呼ぶ
- `oneSide()`：この端末で遊ぶのが1人か（CPU戦・大会・オンライン対戦）。「あなた」と呼ぶ・VICTORY／DEFEAT を出す・自分の席の側だけを見せる。`viewer()` はオンラインなら自分の席（ホスト0・ゲスト1）
- `netWaiting()`：ゲストが結果を待っているあいだは、手番でも「送信しています…」で操作できない
- タイトルのモードに「オンライン対戦」。ロビー（`renderLobby`）：名前、部屋を作る（`lobbyCreate`）／コードで入る（`lobbyJoin`）、コードの表示とコピー（`netCopyCode`）。使えないページ（claude.ai の公開ページ）では、代わりに GitHub Pages 版へのリンク（`NET.PLAY_URL`）を出す
- つながったら `netStartHost`・`netStartGuest` が Host・Guest を作る。ホストはゲストの操作のあと `netRefresh` で描き直し、ゲストは state が届くたび `netGuestState` で差し替えて、新しい演出だけを見せる（`playFx` は「どこまで見せたか」を番号 `app.fxSeen` で覚えているので、そのまま使える）
- 配置：それぞれ自分の画面で配置する。配置完了のあと（ゲストは送ったあと）は動かせず、「相手の配置を待っています」。相手が配置を終えたかも出す（`netSetupLocked`・`netFoeReady`）
- やめる：試合の途中なら確かめる（`netQuitModal`）。相手が抜けた・切れたら `netGone` で知らせる（決着のあとなら結果の画面のまま、試合の前ならロビーへ、試合中ならタイトルへ）。ページを閉じるときは `bye` を送る
- 公開ページの更新（ホットリロード）では、オンライン対戦は引き継がない（通信が切れるため）

### そのほか

- build.js：`/*NET*/` に net.js を差し込む（engine.js のすぐ後。net.js は engine を使うため）
- template.html：ロビーの見た目（`.lobby-panel`・`.lob-card`・`.room-code` など）と、待っている表示（`.net-wait` の点々）

## 7. テスト

| 何を | コマンド | 時間 | 確かめること |
| --- | --- | --- | --- |
| 模擬テスト（通信なし） | `node test/net_sim.js [試合数]`（既定24） | 24試合で約30秒 | ホストとゲストを同じプログラムの中で動かし、CPU に両者の手を選ばせて決着まで。①ゲストに送ったどのスナップショットにも秘密がない（送ってよい項目の一覧）、②決着後にゲストが受け取った全部がホストと同じ、③ホストの記録をやり直す（ふつうの試合と同じ流れ）と同じ結果、④ルールにない操作・変な形のデータ・違う版・満員などを断り、盤面が変わらない |
| 画面テスト（通信あり） | `python3 test/online_e2e.py` | 約2分 | この環境に PeerServer（npm の `peer` 1.0.2）を立て、ブラウザを2つ（ホスト＝PC幅・ゲスト＝スマホ幅）開いて、部屋を作る → 入る（小文字・ハイフン入りのコード）→ ない部屋・満員の部屋に3人目が断られる → 配置（ゲストが先）→ ドラフト → 対戦（アイテム・わざと外すアンサーと差し出し）→ 決着 → リプレイ → もう一度（ホストが先に配置。ワープ・ステルスも使う）→ 決着 → もう一度 → ゲストが途中で退出。最後に、claude.ai の公開ページのふり（`window.claude` を置く）をして、部屋を作れず GitHub Pages 版へのリンクが出ることも。ゲストの手元にホストの秘密が一度も届かないこと、決着後の両者の対戦が同じこと、勝ち負けの表示が逆なことも |

- PeerServer と PeerJS は `SB_NETDEPS`（既定 /tmp/sb_netdeps）に npm で入れる（なければテストが入れる）。この環境は IPv6 が使えないので、サーバーは 127.0.0.1 で立て、ページは `?peer=127.0.0.1:9000` で開く。PeerJS の本体（CDN）は、テストの中で手元のファイルに差し替える。同じ機械の2つのブラウザが直接つながれるよう、Chromium は `--disable-features=WebRtcHideLocalIpsWithMdns` で起動する
- 結果（2026-10-25）：net_sim 48試合すべて OK（ホストの勝ち 23／48。ゲストの CPU は伏せた盤面だけで考えても同じくらい強い＝CPU が隠れた情報を使っていない）。1試合のメッセージは平均81通・合計約0.9MB（1通10KBほど）。online_e2e も OK
- 本物の回線（PeerJS の無料クラウド・別々の端末と回線）は、この環境から出られないので、ユーザーが試す

## 8. 遊び方（知り合いと試すとき）

1. 2人とも、GitHub Pages のゲーム（ランチャーの「サーチバトル」）を開く。claude.ai の公開ページでは使えない（安全のため、WebRTC とほかのサイトへの通信が止められている。オンライン対戦を選ぶと、GitHub Pages 版へのリンクを出す）
2. 2人ともタイトルのモードで「オンライン対戦」を選ぶ。部屋を作る人は、ルール（4×4／5×5）とアイテムの設定も選ぶ
3. 「オンライン対戦の部屋へ」→ 名前を入れる。部屋を作る人は「部屋を作る」を押し、出てきた6文字のコードを LINE などで相手に伝える
4. 相手は「部屋に入る」にコードを入れて「入る」。つながると配置の画面になる
5. 終わったら、部屋を作った人が「もう一度」で次の試合を始められる。やめるときは「退出する」（試合の途中は「やめる」）

つながらないとき：Wi-Fi どうし／モバイル回線どうしなど、組み合わせを変えて試す（会社・学校のネットワークは、直接のつながりを止めていることがある）。PeerJS の無料クラウドが止まっていると、部屋を作れない（「仲介サーバーにつながりません」）。

## 9. 限界と今後（v2 以降）

- ホストはのぞける（v1 の割り切り）。防ぐなら、それぞれが自分の盤面だけを持ち、相手の操作に自分の端末が答える形（B'）に作り変える。試合の最後に配置を見せ合えば、途中で嘘をついていないかも確かめられる
- 直接つながらない回線がある。PeerJS の TURN（中継）は無料で制限がある。自分で TURN を用意するなら `peerOptions` の `config.iceServers` に足す
- PeerJS の無料クラウドには動き続ける保証がない。止まっているときはオンライン対戦だけが使えなくなる
- 通信が切れたら試合は終わる（再接続なし）。スマホでほかのアプリを長く開くと切れることがある（45秒）
- 毎回スナップショットをまるごと送っている（1通10KBほど）。困るほどではないが、差分だけ送る形にもできる
- 再接続、観戦、大会モードのオンライン、知らない人とのマッチングは v2 以降

## 10. コードの読み方（おすすめの順番）

1. src/net.js の ②（`redactFor`）：何を伏せているか。表の5と見比べる
2. src/net.js の ④（`Host.prototype._act`・`Guest.prototype.receive`）：ホストがゲストの操作を確かめて実行し、ゲストが結果を受け取るところ
3. src/ui.js の `act()`：同じボタンが、ふつうの試合・ホスト・ゲストで違う動きになるところ
4. src/ui.js の `netStartHost`・`netStartGuest`・`netGuestState`：つながってから画面が動くまで
5. test/net_sim.js：上のしくみを、通信なしでまとめて確かめている
