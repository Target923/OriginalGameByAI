# サーチバトル オンライン対戦の設計（めっちゃカメレオン型・P2P）

2026-10-25 作成。まだ作っていない（次のセッションで作る）。作るときの設計図と、しくみを学ぶための説明を兼ねる。

## 1. ねらいと範囲

- **v1（最初に作るもの）**：1vs1 の単発試合をオンラインで遊べるようにする。ルール（予選4×4・決勝5×5）とアイテムの設定は、部屋を作った人が決める。大会モードは対象外。
- **方式**：部屋を作った人（**ホスト**）の端末が審判をする。相手（**ゲスト**）は操作を送り、判定の結果を受け取って画面を描く。
- **サーバー代は0円**：つなぎ役に PeerJS の無料クラウドを使い、試合のデータは端末どうしで直接やりとりする（ブラウザに入っている WebRTC）。めっちゃカメレオンが EOS（無料のマッチング・中継）を使い、部屋を立てた人の PC がサーバー役になっているのと同じ考え方。
- **割り切り**：ホストは、開発者ツールを使えば相手の配置をのぞける。知り合いどうしで遊ぶ前提。ゲストには見てよい情報しか送らないので、ゲストはのぞけない。ゲストが改造したゲームで操作を送っても、ホストのルールのプログラムが確かめるので、ルールにない手は通らない。

## 2. 用語（勉強用）

| 用語 | 意味 |
| --- | --- |
| P2P（ピア・ツー・ピア） | サーバーを通さず、端末どうしが直接つながること |
| WebRTC | ブラウザに最初から入っている、端末どうしを直接つなぐ機能。ビデオ通話にも使われる。ここでは文字のデータを送る「データチャネル」だけを使う |
| シグナリング | 直接つながる前に、お互いの「住所」（つなぎ方の情報）を交換すること。これだけは仲介役が要る。PeerJS の無料クラウドがその役 |
| STUN・TURN | STUN＝自分の外から見た住所を教えてもらうしくみ（無料で使えるものが多い）。TURN＝直接つながらないときにデータを中継するしくみ（帯域を使うので無料のものは少ない） |
| ホスト権威（host-authoritative） | 本当の盤面を持って判定するのはホストだけ、という作り方。ゲストの端末は「見てよい情報」で画面を描くだけ |
| スナップショット | ある時点のゲームの状態をまるごと写したデータ。ホストが判定のたびにゲスト向けのものを作って送る |
| 伏せる（redaction） | ゲストに送るスナップショットから、ゲストが知ってはいけない部分（ホストのキューブの位置など）を取り除くこと |

## 3. 全体の流れ

```
 ホスト（審判）              PeerJS の無料クラウド          ゲスト
 ─────────────              ───────────────────          ─────────────
 部屋を作る ───登録 "searchbattle-K7P2QX"──▶
 部屋コード K7P2QX を表示
                                            ◀──"searchbattle-K7P2QX" を探す── コードを入力
           ◀════════ WebRTC で直接つながる（ここから先、クラウドは使わない）════════▶
           ◀──────────────── hello（アプリ名・バージョン・名前）─────────────────
 ──────────────── welcome（試合の設定：ルール・アイテム・名前）────────────────▶
 配置する                                                  配置する（自分の画面の中だけ）
           ◀──────────── setup（形・向き・位置・トレジャーのマス）──────────────
 ルールで確かめて反映
 ────────────────── state（ゲスト向けに伏せたスナップショット）──────────────▶
 対戦：ゲストの手番
           ◀──────────────── act（例：call、マス 5）──────────────────────
 g.call(1, 5) で判定
 ────────────────── state（結果。新しい演出の記録も入る）───────────────────▶  演出を見せて描く
 対戦：ホストの手番
 g.useItem(0, ...) で判定
 ────────────────── state ─────────────────────────────────────────────▶  演出を見せて描く
 決着
 ────────────────── full（伏せない全部。答え合わせとリプレイ用）──────────────▶
```

## 4. メッセージ（通信の約束ごと）

どれも `{ t: '種類', ... }` の形の小さなデータ。PeerJS の既定の送り方（binary）は大きなデータを自動で分けて送るので、スナップショットもそのまま送れる。

| t | 向き | 中身 | いつ |
| --- | --- | --- | --- |
| `hello` | ゲスト→ホスト | `app: 'searchbattle'`、`v`（エンジンのバージョン）、`name` | つながった直後。バージョンが違えば断る |
| `welcome` | ホスト→ゲスト | 試合の設定（`rules`・`items`・`draftEach`）、両者の名前、ゲストの席（1） | hello を受けたら |
| `setup` | ゲスト→ホスト | `pieces: [{ key, t, r0, c0 }]`、`treasure`（マス） | ゲストが配置完了を押したとき |
| `act` | ゲスト→ホスト | `name`（`call`・`useItem`・`answer`・`skipCall`・`endTurn`・`treasureCall`・`sacrifice`・`draftPick`）、`args`、`seq`（何番目の操作か） | ゲストが操作したとき |
| `state` | ホスト→ゲスト | `snap`（伏せたスナップショット）、`seq` | ホストが何か判定するたび |
| `reject` | ホスト→ゲスト | `reason`、`seq` | ゲストの操作がルール上できなかったとき（ふつうは画面側で防ぐので、まれ） |
| `full` | ホスト→ゲスト | 伏せないスナップショット（リプレイの記録 `actions` も入る） | 決着したとき |
| `bye` | どちらも | なし | やめるとき |

## 5. ゲストに送らないもの（伏せる）

ルールのプログラム（src/engine.js）は、もともと「本人だけに見せる情報」を分けて持っているので、それを使う。

| 場所 | 伏せ方 |
| --- | --- |
| ホストの `players[0].pieces` | 生きているキューブ（破片も）は消す。撃破されたキューブは公開済みなので残す |
| ホストの `players[0].treasure` | 消す |
| ホストの `players[0].splitPieces` | 空にする（バズーカで分解された元の形。画面でも相手の分は出していない） |
| `actions`（リプレイの記録） | 消す（配置の座標が入っているため）。決着後の `full` で渡す |
| `rng`・`initOpts` | 送らない（乱数はホストだけが使う） |
| `events`（演出の記録） | 数と順番はそのまま（ゲストの画面が「どこまで見せたか」を番号で覚えているため）。ホストの操作の `priv`（ワープの移動先・ステルスをかけたマス）は消す |
| `log` | ホストの行の `priv`（本人向けの詳しい文）は消す |
| `lastAction` | ホストのワープ・ステルスの `result`（マス）は消す |
| そのほか | バズーカの演出・ログに、持ち主だけが知る情報（分解した個体を失ったかどうか）が入っていないか、作るときに確かめる |

自動テストで、**どの場面のスナップショットにも、ホストの生きているキューブのマス・トレジャーのマスが入っていない**ことを確かめる。

## 6. プログラムの変更点

- **src/net.js（新しく作る）**
  - PeerJS の読み込み（オンライン対戦を選んだときだけ）。CDN：`https://cdn.jsdelivr.net/npm/peerjs@1.5.5/dist/peerjs.min.js`
  - 部屋を作る（6文字のコード。まぎらわしい文字 0・O・1・I は使わない）・コードで入る・送る・受け取る・切れたときの知らせ
  - `redactFor(game, seat)`（伏せたスナップショットを作る）、`restore(snap)`（スナップショットからゲームを作り直す。テストの invariants.js がやっている「保存して読み込み直す」と同じ方法）
  - 接続先は URL の `?peer=localhost:9000` で切り替えられるようにする（テストでこの環境に立てたサーバーを使うため）
- **src/ui.js**
  - タイトルに「オンライン対戦」。ロビーの画面（ニックネーム、部屋を作る／コードを入力して入る、待っている間の表示）
  - `viewer()`：オンラインなら自分の席（ホスト0、ゲスト1）
  - CPU の手番の処理（`cpuRun`）はオンラインでは動かさない
  - **操作の窓口 `act(name, ...args)` を作る**：今は `g.call(v, c)` などを13か所で直接呼んでいる。これを窓口経由にし、ふつうの試合ではそのまま実行、ゲストなら送信して `state` を待つ（待っている間は操作できない）
  - ホスト：ゲストの `act` を受けたら、席と手番を確かめて実行し、画面を更新して `state` を送る。自分の操作のあとも `state` を送る
  - ゲスト：`state` を受けたら、ゲームを差し替えて、新しい演出だけを見せて描く（`playFx` は「どこまで見せたか」を番号で覚えているので、そのまま使える）
  - 配置：それぞれ自分の画面で配置する。ゲストは配置完了で `setup` を送り、ホストの確認を待つ
  - 通信が切れたら知らせて、タイトルに戻る（v1。再接続は v2）
- **build.js**：net.js を差し込む。**template.html**：ロビーの画面の見た目

## 7. テスト

1. **Node（通信なし）**：ホストとゲストを同じプログラムの中で動かし、メッセージを直接渡す模擬テスト。CPU に両者の手を選ばせて決着まで進め、ふつうの試合と同じ結果になること、ゲストに渡したスナップショットに秘密が入っていないことを確かめる
2. **画面（通信あり）**：この環境に PeerServer（npm の `peer`）を立て、Playwright でブラウザを2つ開いて、部屋を作る → 入る → 配置 → 対戦 → 決着までを通す
3. **ユーザーの確認**：本物の PeerJS で、別々の回線・端末からつながるか（この環境からは外のサービスに出られないため）

## 8. 限界と今後

- ホストはのぞける（v1 の割り切り）。防ぐなら、それぞれが自分の盤面だけを持ち、相手の操作に自分の端末が答える形（B'）に作り変える。試合の最後に配置を見せ合えば、途中で嘘をついていないかも確かめられる
- 直接つながらない回線がある（会社のネットワーク、一部のスマホ回線など）。中継（TURN）が要るが、無料のものは制限がある
- PeerJS の無料クラウドには動き続ける保証がない。止まっているときはオンライン対戦だけが使えなくなる
- 再接続、観戦、大会モードのオンライン、知らない人とのマッチングは v2 以降
